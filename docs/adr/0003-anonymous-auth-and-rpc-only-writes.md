# 익명 인증을 자동 생성하고, 제보·투표는 RPC를 통해서만 쓴다

"5초 안에 제보"와 "악성 제보 방어"가 정면충돌한다. 회원가입 화면을 세우면 5초가 깨지고, 완전 익명이면
rate limit도 중복 판정도 불가능하다. Supabase 익명 인증을 첫 실행 시 백그라운드로 생성해서, 유저는
로그인 화면을 보지 않지만 서버는 안정적인 `user_id`를 갖는 구조를 택했다.

방어는 클라이언트가 테이블에 직접 INSERT하지 못하게 막는 것에서 시작한다. RLS는 "이 유저가 쓸 수 있나"만
판단하고 "이 좌표가 말이 되나"는 보지 못하기 때문에, 모든 쓰기를 `SECURITY DEFINER` RPC로 통과시킨다.

## Considered Options

기기 무결성 검사(App Attest / Play Integrity)는 더 강하지만 1인 개발 MVP에 무겁고 루팅 기기·에뮬레이터의
정상 유저를 잘라낸다. 실제 어뷰징이 관측된 뒤에 붙이는 것이 순서다.

## Consequences

- RPC에서 검사하는 것: 직전 제보 대비 이동 속도(시속 900km 초과 시 거부), 계정당 빈도 제한,
  Android `expo-location`의 `mocked` 플래그, 투표자와 제보 위치 간 거리.
- `mocked` 플래그는 Android에만 있다. iOS 스푸핑은 이 수단으로 못 잡는다는 것을 알고 쓴다.
- 앱 재설치하면 새 익명 계정이 생긴다. 작정한 공격자는 막지 못하며, 실질 방어선은 계정이 아니라
  좌표-속도 검증과 밀도 이상 탐지다.
- 제보 실패가 정상적으로 발생한다(rate limit, 속도 검증). 낙관적 업데이트를 롤백할 때는 반드시 사유를
  보여줘야 하며 조용히 되돌리면 안 된다.

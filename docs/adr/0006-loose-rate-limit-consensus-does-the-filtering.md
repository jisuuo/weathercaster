# 제보 제한을 느슨하게 두고, 걸러내는 일은 합의 집계에 맡긴다

제보 rate limit을 10분으로 잡았다가 근거를 확인하고 30초 + 하루 100건으로 완화했다. 미래의 독자가
"제한이 왜 이렇게 헐겁지, 버그 아닌가"라고 볼 만한 값이므로 이유를 남긴다.

## 근거

**기상청 실황은 40~100분 지난 데이터다.** 초단기실황(`getUltraSrtNcst`)은 1시간에 한 번 갱신되고,
`base_time`이 정시이며 API 제공은 매시 40분경이다. 오후 3시 35분에 앱을 켜면 받는 값은 오후 2시 관측이다.
**이 40~100분이 이 앱의 가치 구간 전부다.** 그리고 소나기는 보통 몇 분에서 30분이면 지나간다 — 2시간을
넘기면 소나기로 분류하지도 않는다. 즉 가치 구간 안에서 날씨는 여러 번 바뀐다. 10분 제한은 우리가 가진
유일한 해상도를 스스로 깎는 것이었다.

**mPING은 30초에 1건을 허용한다.** NOAA/NSSL이 운영하는 크라우드소싱 날씨 제보 시스템으로 이 분야에서
가장 진지한 선례다. 계정조차 없다 — "Reporters are anonymous, so tracking is unavailable." 개별 제보를
검증하는 대신 다수 일치에 의존한다 — "crowdsourcing consistency essentially defines the first level QC
process."

**우리는 이미 같은 QC를 쓰고 있다.** `nearby_summary`와 `reports_in_bounds`는 모두
`count(distinct user_id)`로 센다. 한 명이 100건을 올려도 합의 강도는 1이고, 지도는 격자 단위로 집계된다.
**즉 도배로 지도를 오염시키는 경로는 rate limit이 아니라 집계 방식이 막고 있다.**

## 결정

rate limit에 남는 실제 역할은 지도 오염 방지가 아니라 쓰기 폭주와 저장 비용 억제뿐이다. 그 약한 목적을
위해 제품의 핵심 해상도를 팔지 않는다.

- 최소 간격 30초 — 클라이언트 버그로 인한 중복 전송 방어가 목적
- 하루 100건 — 저장 비용 상한
- **같은 유저·같은 격자·같은 상태의 재제보는 새 행을 만들지 않고 기존 제보의 수명을 연장한다**

## Consequences

- 수명 연장 분기 덕분에 도배해도 행이 늘지 않는다. 동시에 "아직도 비 온다"는 신호가 살아나, 반복 제보가
  노이즈가 아니라 정보가 된다.
- 상태가 바뀐 제보는 언제나 새 행이므로, 소나기가 그친 순간이 지연 없이 잡힌다.
- 제한을 조일 필요가 생긴다면 그때는 rate limit이 아니라 집계 가중치를 손보는 쪽이 맞다. rate limit을
  조이면 어뷰징보다 정상 사용이 먼저 막힌다.
